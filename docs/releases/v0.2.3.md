# Tethermark Community Edition 0.2.3

This patch release corrects static-audit evidence classification, provider selection, finding deduplication, score labeling, and placeholder-secret handling. It does not change the Community Edition UI layout, persistence schema, export schema, supported-platform contract, or provider policy.

## Highlights

- Static-only evidence cannot be presented as runtime validation or runtime strengthening.
- Run completion records distinguish the overall score from the static baseline score, and the summary card explicitly labels the overall score.
- Static evidence plans execute only registered, mode-compatible providers and always retain deterministic repository analysis.
- Equivalent cross-standard and cross-provider findings merge before scoring and persistence; sharing a source symbol alone does not make distinct findings duplicates.
- Placeholder credential values are redacted and treated as medium-severity review signals instead of confirmed critical disclosures.

## Installation and update

Use only the immutable `v0.2.3` tag or the verified files attached to the GitHub release. Before updating, stop Tethermark and create a verified backup:

```bash
npm run scan -- backup create --reason before-upgrade
```

Then follow the ref-pinned Windows or macOS/Linux update procedure in [Installation](../installation.md#update-and-rollback).

## Compatibility and boundaries

- SQLite persistence schema `1.3.0` and export schema version 1 are unchanged.
- Static audits remain supported on Windows, macOS, and Linux.
- Executable runtime validation retains the documented Windows Docker Desktop and Linux Docker/rootless Podman/gVisor boundaries. Real macOS container execution remains deferred.
- Runtime validation still requires an isolated backend and never falls back to unisolated host execution.
- Local Codex with a ChatGPT subscription remains the default interactive model path. API-key providers remain optional and are required for unattended model work.
- No hosted tenancy, managed identity, metered sandbox, Cloud connector, or managed notification capability is added.

## Validation summary

The patch passed the complete regression suite, production static-readiness workflow, and a subscription-backed static acceptance audit. The acceptance record executed exactly four registered static providers, produced zero duplicate groups, produced zero runtime-validated or runtime-strengthened findings, and retained redacted medium-severity placeholder-secret evidence. Main-branch CI passed verification and Ubuntu, Windows, and macOS smoke jobs before release preparation.

Official release files must come from the tag-bound **Signed Release Artifacts** workflow and pass checksum, manifest, CycloneDX, SLSA provenance, and SBOM-attestation verification before publication.

## Rollback

The immutable `v0.2.2` release is the code rollback target for `v0.2.3`.

1. Stop API, web, worker, and scheduled processes.
2. Verify the pre-upgrade backup with `npm run scan -- backup verify --backup <backup-directory>`.
3. Run the documented update command with `-Ref v0.2.2` on Windows or `--ref=v0.2.2` on macOS/Linux.
4. Confirm the rolled-back application can read the existing database before considering a backup restore; the persistence schema is unchanged.
5. Never merge or edit SQLite files manually. Preserve failed state for diagnosis and follow [Persistence Failure Recovery](../persistence-failure-recovery.md).

Rolling back code does not revoke provider credentials, delete exported files, or undo external actions. Follow [Data Lifecycle and Privacy](../data-lifecycle-and-privacy.md) for credential removal and external cleanup.
