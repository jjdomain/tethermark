# Tethermark Community Edition 0.2.2

Status: release candidate; not yet tagged or published.

## Highlights

- Adds candidate-bound lifecycle/recovery verification for fresh install, update, guarded uninstall, clean two-ref upgrade, backup/restore, cancellation/retry, restart recovery, policy migration, and export compatibility.
- Prevents a rolled-back System Policy export from importing a newer superseded version. Policy exports now declare same-major additive compatibility; legacy metadata-free version 1 exports remain accepted and future major versions fail closed.
- Restores bounded, operator-approved validation-lane narrowing for live Codex/ChatGPT-session audits without widening model or package budgets.
- Preserves real static scanner coverage in copied sandboxes and binds Scorecard evidence to the audited target commit.
- Extends candidate-ref native-runtime verification and awaits asynchronous terminal persistence in the regression harness.

The existing Community Edition UI layout and provider controls are unchanged. Local Codex with a ChatGPT subscription remains the default interactive model path; API-key providers remain optional and are required for unattended model work.

## Installation and update

Do not use `v0.2.2` until the tag is published. Before updating, stop Tethermark and create a verified backup:

```bash
npm run scan -- backup create --reason before-upgrade
```

Then follow the ref-pinned Windows or macOS/Linux update command in [Installation](../installation.md#update-and-rollback). The installer must resolve the published tag to one detached commit and preserve checkout-local configuration and state.

## Compatibility and data behavior

- The supported Node/npm, Python, browser, scanner, and runtime ranges remain those in [Supported Platforms](../supported-platforms.md).
- SQLite remains the only release-supported Community Edition database. Persistence schema `1.3.0` is unchanged from `v0.2.1`.
- Run records, immutable policy snapshots, review history, learning approvals, artifacts, and exports retain their existing storage and retention boundaries.
- Export schema version 1 remains same-major additive. System Policy import now rejects an incompatible schema name or major version before persistence.
- No hosted tenancy, managed identity, metered sandbox, Cloud connector, or managed notification capability is added by this release.

## Runtime and provider boundaries

- Static audits remain supported on Windows, macOS, and Linux.
- Executable local runtime validation remains certified only for the retained Windows Docker Desktop and Linux Docker/rootless Podman/gVisor boundaries. Real macOS container execution remains deferred and must not be inferred from the macOS boundary job.
- Runtime validation requires an actual isolated backend and never falls back to unisolated host execution.
- Local Codex/ChatGPT-session credentials are for operator-started work. Unattended model workloads require an approved API-key provider policy. Mock results remain test/fixture evidence and must not be presented as live model validation.

## Rollback

The immutable `v0.2.1` release is the code rollback target for `0.2.2`.

1. Stop API, web, worker, and scheduled processes.
2. Verify the pre-upgrade backup with `npm run scan -- backup verify --backup <backup-directory>`.
3. Run the documented update command with `-Ref v0.2.1` on Windows or `--ref=v0.2.1` on macOS/Linux.
4. Because persistence schema `1.3.0` is unchanged, first confirm the rolled-back application can read the existing database. Restore the verified pre-upgrade backup only if rollback validation requires it.
5. Never merge or edit SQLite files manually. Preserve a failed or corrupt current database for diagnosis and follow [Persistence Failure Recovery](../persistence-failure-recovery.md).
6. Re-run first-run/doctor, export compatibility, and the operator smoke workflow before resuming unattended work.

Rolling back code does not revoke provider credentials, delete externally delivered webhooks, remove exported files, or undo external actions. Follow [Data Lifecycle and Privacy](../data-lifecycle-and-privacy.md) for credential removal and external cleanup.
